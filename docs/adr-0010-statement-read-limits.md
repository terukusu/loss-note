# ADR-0010: 本番の決済明細の読み取りは、Firestore の日の文書で回数と費用の上限を予約してから送り、資格情報は Secret Manager の入れ物 1 つに置く

- 状態: 採用（決定 5・6 の資格情報の方式と Cloud Run への載せ方は ADR-0011 で上書き。決定 1 の「上限は 2 つ・値はコードの定数」は ADR-0014 で上書き）
- 日付: 2026-11-18
- 関連: Issue #44（本番で決済明細の読み取りを動かす）、EPIC #45、ADR-0005（読み取りの入口）、ADR-0004（起動の判定）、ADR-0008（本番の土台）、ADR-0009（本番のデプロイ）、設計書 7.5・8.2・10 章・12 章・13.4、`infra/README.md`「明細の読み取りの資格情報」

## 背景

本番で読み取りを動かすと、「お金が出ていく口」（従量課金の AI）と「鍵が漏れる口」（API キー）を同時に開ける。GCP の予算（ADR-0008）は Anthropic の請求を見ない。画面の不具合での連打・盗まれたトークン・利用者の増加で、気づかないまま請求が膨らまないよう、送る前に止める天井が要る。Cloud Run は最小 0 のインスタンスなので、記憶の中の数は冷えるたびに消える。

## 決定

1. **上限は 2 つ。利用者ごとの回数（1 日 30 回）と、全利用者の合計の費用（1 日 2.00 USD）**。日の区切りは日本時間の 0:00（UTC+9 の固定）。越える要求は AI を呼ばずに 429 `read_limited`。回数と費用のどちらで止まったかは応答に出さず、ログの理由（`limited_user` / `limited_spend`）だけで分ける。値はコードの定数（`api/src/loss_note_api/read_limits.py`。環境変数で変えない）。手元の開発にも同じ上限を掛ける
2. **数える場所は Firestore の日の文書**: 利用者ごと `users/{uid}/statement_read_days/{YYYY-MM-DD}` = `{count}`、全体 `statement_read_spend/{YYYY-MM-DD}` = `{count, microUsd}`。#42 の既定のデータベースに置き、実行用 SA の `roles/datastore.user` で足りる（付与を増やさない）。2 つの文書を 1 つのトランザクションで読み、判定し、送るときだけ書く（同時の要求でも上限を越えて送らない）。読めない・書けないときは AI を呼ばずに 503 `read_unavailable`（閉じる側）。残すのは日付・回数・金額だけ
3. **予約と精算**: 送る前に、その要求の費用の上界（予約額）を足して `計上額 + 予約額 ≤ 2.00 USD` のときだけ送る（等しいときは送る）。送った後は「使ったトークン × 料金表」と「SDK の合計額」の大きい方に直す（手元の実測で SDK の合計額が料金表より約 26% 大きかったので、多めに数える側を取る）。どちらも受け取れなかった回（締め切り超え・途中の失敗）は予約額のまま。精算は予約した日の文書へ（0:00 をまたいでも同じ日）。精算の書き込みに失敗しても応答は変えない（予約額が残る = 多めの側）。金額は整数の µUSD（単価の USD / 100 万トークン = µUSD / トークン）で、浮動小数の誤差を出さない
4. **予約額 = 入力の上界 × 入力の最高単価 + 最大出力 × 出力の単価**（`packages/statement-read/src/statement_read/pricing.py`。料金表は評価の道具と共有する）。入力の上界は、画像 1 枚の上界 ceil(2,000 × 2,000 / 750) = 5,334 トークン + 指示・決まった文・ツールの定義の UTF-8 のバイト数（トークン数 ≤ バイト数）+ CLI が足す分の上乗せ 20,000 トークン。入力の最高単価は 1 時間の cache 作成（入力の 2 倍）。**最大出力は CLI に `CLAUDE_CODE_MAX_OUTPUT_TOKENS` = 16,000 を渡して抑える**（`app_settings.APP_MAX_OUTPUT_TOKENS`）。結果（`report_statement` の入力）の最も長い形（20 行・銘柄の名前 40 字の漢字・手数料 8 欄・桁の多い数）でも JSON を整形して約 15,000 B で、合成 14 枚の実測の出力は平均 720 トークン以下。Sonnet 5.5 で予約額は 278,736 µUSD（約 0.28 USD）になり、計上 0 から同時に 7 枚まで送れる
5. **本番の資格情報は Anthropic API のキーだけ**（本番専用のワークスペースのもの）。Secret Manager の入れ物 `statement-read-anthropic-api-key` 1 つ（東京だけに複製・削除の防止 PREVENT）を所有者の apply（`infra/bootstrap/statement_read_credentials.tf`）で作り、読めるのは実行用 SA だけ（入れ物の単位の `secretAccessor`）。CI の SA には付けない。版（値）は Terraform で宣言しない（state・plan に値を入れない。`.github/scripts/secret-check.sh` が版の宣言 0 件を見る）。値はオーナーが GCP のコンソールの Secret Manager の画面で新しい版として貼る（キーの値をターミナル・会話・ログに通さない）。本番の起動（verify）で `STATEMENT_READ_CREDENTIAL` が `oauth_token` なら使えない設定（503）にする
6. **Cloud Run への参照は切り替えの変数で付ける**（`infra/prod` の `statement_read_key`。CI は repository variable `STATEMENT_READ_KEY` が `true` のときだけ true を渡す。CI の値は secrets に置く決まり（ADR-0009）の例外で、秘密ではない真偽の切り替えだけを variables に置く。secrets にするとログの `true` がすべて伏せ字になるため）。参照はインスタンスの起動時に解決され、版が無いとインスタンスが起動しないので、キーの版を入れる前は参照を付けない（読み取りは 503・ほかの機能は動く）
7. **見張り**: 日ごとの回数・金額は本番の Firestore の計上の文書から所有者の資格情報で読む。本番のキーの属するワークスペースに Anthropic Console の月の上限 20 USD を置く（日の上限が働かない不具合への二重の安全弁。オーナーの手作業）

## 選択肢

- **記憶の中で数える**: 採らない。最小 0 のインスタンスでは冷えるたびに消え、最大 2 のインスタンスの間で数が分かれる
- **出力の上限を渡さず、モデルの最大出力（128,000）で予約額を出す**: 予約額が約 1.40 USD になり、全体の上限 2.00 USD の中で同時の 2 枚目が費用の側で 429 になる。採らない（Phase 2 の計画から変えた。CLI 2.1.316 が `CLAUDE_CODE_MAX_OUTPUT_TOKENS` をモデルの最大出力を上限に要求の max_tokens にすることを同梱の CLI で確かめた）
- **全体の上限を 3.00 USD に上げて、同時の 2 枚を通す**: 天井そのものを上げるので採らない（最大出力を抑えられたため）
- **料金表の額だけで精算する**: 手元の実測で SDK の合計額の方が大きく、少なく数える側に寄るので採らない
- **上限の値を環境変数で変えられるようにする**: 設定の誤りで上限が外れる経路ができるので採らない
- **キーの参照を最初から付ける**: 版の無い参照ではインスタンスが起動せず、キーが入るまでデプロイが壊れるので採らない
- **版を Terraform で宣言する**: 値が state・plan に入るので採らない

## 結果

- 読み取り 1 回ごとに Firestore のトランザクション 1 回（読み 2・書き 2）と精算の書き込み 1 回が増える（数十 ms。読み取りの 5 秒の目安の内側）
- 同じ日の文書を読んで書くトランザクションが多く重なると、エミュレーターでは競合で再試行を使い切って 503 になりうる（閉じる側。越えて送ることはない）。本番の利用者 1 人では起きにくい
- 予約額の正しさは、CLI が `CLAUDE_CODE_MAX_OUTPUT_TOKENS` を守ることと、CLI が足す入力が 20,000 トークンに収まることと、要求が 1 回であることに寄りかかる。同梱の CLI 2.1.316 のソースでは、応答が最大出力で止まる（`stop_reason = max_tokens`）と「続きを書け」という要求を最大 3 回続けて出す（回復。止める環境変数は無い）。最も長い形の結果でも最大出力に収まる大きさにしたので通常は起きないが、起きた回は最大 4 回の要求の分（1 回の予約額の数倍）を使いうる。外れた回も精算は実額（料金表と SDK の大きい方。SDK の合計額は回復の要求も含む）なので、その日の計上は正しく、越えるのはその 1 回の分だけ。Console の月の上限が二重の安全弁。本番では日ごとの `microUsd / count` ≤ 予約額 を確かめる。CLI の版を上げるときは同梱の CLI がこの変数を読むこと・回復の回数を確かめ直す
- 結果が 16,000 トークンを超える明細は読み取りが失敗する（502。手で入れられる）。最も長い形でも収まる大きさにした
- 全利用者の要求が同じ日の全体の文書 1 つをトランザクションと加算で書く（読み取り 1 回で 2 回）。Firestore の 1 文書の書き込みの目安（毎秒 1 回程度）に近づくと競合で 503（閉じる側）になる。利用者が増えて同時の要求が増えたら、全体の計上を分割カウンタにする
- 計上の文書は利用者の削除（設計書 10.1 のアカウントの削除）の対象に含める（削除の実装は後の Issue）
- 利用者ごとに上限を変える・課金は課金の EPIC。AI の振り返り（8.1）を同じ上限に入れるかはその Issue で決める。チャートの時間足の読み取り（#27）は同じ上限（同じ財布）で数える（ADR-0015）
