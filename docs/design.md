## 1. なぜ作るか

裁量トレードで最も大切なのは **損失のコントロール**。「エントリーの根拠が崩れた」と判断できる状態になったときに決済できていて、かつ損失が許容範囲（資金の 1〜2%）に収まっていること。

それには、ポジションを持つ時点で次の 4 つを決めておく必要がある。

1. 明確な **エントリーの根拠**
2. その根拠が **崩れる条件 = LC**（金額ではなく、思惑が外れたと確認できる価格）
3. **TP**（エントリー時の根拠からの推定でよい）
4. LC での損失が資金の 1〜2% に収まる **数量**

loss-note は、それが **できているかを振り返り、客観視し、心理的な影響を排除できるようになるための道具**。

### 1.1 既存の道具との違い

一般的なトレード日誌（スプレッドシート・日誌アプリ）は **結果**（損益・勝率）を記録する。loss-note は **計画と実行の差** を記録の中心に置く。

| | 一般的なトレード日誌 | loss-note |
|---|---|---|
| 記録の単位 | 約定と損益 | 計画（入る前に決めたこと）→ 実行（実際にしたこと） |
| 良し悪しの物差し | 勝ったか負けたか | 計画どおりだったか（勝っても計画外なら悪い取引、負けても計画どおりなら良い取引） |
| 損失の分類 | 自己申告 | 計画と実行の記録から自動で判定（5.3） |
| 心理 | 自由記述 | 感情のタグと見送りの記録で、規律が崩れるときの心理をデータで見る |
| 入らなかった取引 | 残らない | 見送りとして残す（躊躇・感情・入っていたらどうなったか） |

### 1.2 オーナーのシートで見えていた課題（2026-11-17 の観察。件数は記載しない）

- 損益・為替を手で入れていて、LC の書き間違い（桁落ち）がある
- 計画（LC・TP）と結果が同じ行にあり、LC を後から動かしたか、記録が後付けかが分からない
- 気づきが取引と結び付いておらず、「暴落を見るとお試し買いをする。それもオーバーサイズで。そして負ける」のようなパターンをデータで確かめられない
- 損失種別（A / B）の付け方が、総評の内容と揃っていない行がある
- チャート画像で行が伸び、一覧として読みにくい

## 2. スコープ

### 2.1 MVP と縦切り

| 縦切り | 中身 | 終わったと言える状態 |
|---|---|---|
| 1. 手元で回る | 計画 → 保有中（LC の移動）→ 決済 → 自動判定、見送り、一覧と詳細。SPA + API + Firestore / Auth のエミュレーター | 手元で 1 人の利用者が、計画から振り返りまで一通り使える |
| 2. 本番で回る | 専用の GCP プロジェクト、Terraform、ログイン、デプロイ、オーナーのデータの取り込み | オーナーが本番で毎日の記録に使える |
| 3. 気づきと集計 | 気づきと取引の結び付け、規律の指標（6 章）、ダッシュボード | 「計画どおりだった率」「避けられた損失」が期間・銘柄・セットアップ別に見える |
| 4. AI の振り返り | 取引ごとの振り返りと、期間の振り返り（7 章） | AI が根拠つきで規律の崩れのパターンを指摘する |

縦切り 1 から順に作る。各縦切りが EPIC になる。

### 2.2 受け入れ基準（AC。縦切りの EPIC で細かくする）

- AC1: 計画の入力中に、資金に対するリスク（%）と、許容リスクに収まる最大の数量がその場で出る
- AC2: エントリー後に LC を変えると、変更の時刻・前後の価格・理由が履歴に残り、「広げた（リスクが増えた）」か「詰めた」かが判定される
- AC3: 決済すると、5.3 の規則で判定（A / B / C と理由）と R 倍数が出る。判定は計画と実行の記録だけから決まる（手入力で上書きできるが、上書きした事実は残る）
- AC4: 計画を記録した時刻と、エントリーの時刻の前後が分かる（後付けの計画には印が付く）
- AC5: 見送りを記録でき、一覧・集計で取引と区別される
- AC6: 利用者は自分の記録だけを読み書きできる（他の利用者の記録は API が返さない。テストで固定する）
- AC7: 幅 360px から PC まで、横スクロールなしで使える
- AC8: 損益・リスク・R の計算は純関数で、手計算の例と性質テストで固定されている

### 2.3 スコープ外（MVP では作らない）

- 課金（K5）
- 証券会社・取引所との連携（約定の自動取り込み）。手入力が前提
- 価格・為替の自動取得（為替は手入力。銘柄の通貨が円なら 1）
- 部分決済・ナンピン（1 取引 = 1 回のエントリーと 1 回の決済。分けたいときは別の取引として記録する）
- チームでの共有・他の利用者の記録の閲覧
- スマホのネイティブアプリ（PWA は後段で検討）

## 3. 用語

相場の言葉はそのまま使う。

| 言葉 | 意味 |
|---|---|
| 計画 | ポジションを持つ前に決めること。根拠・崩れの条件・LC・TP・数量・許容リスク |
| 根拠 | なぜここで入るのか。文章 + セットアップのタグ + チャート |
| 崩れの条件 | 根拠が崩れたと判断できる状態の説明（例: 「直近安値の〇〇を割ったらサポートが崩れた」）。LC はこの条件を価格にしたもの |
| 資金 | リスクの分母。利用者が設定する口座の資金。取引ごとに、計画した時点の値を写して持つ |
| 許容リスク | 1 取引で失ってよい資金の割合。既定は利用者の設定（1〜2%） |
| 計画のリスク（1R） | `|イン − LC| × 数量 × 乗数 × 為替`（円） |
| R 倍数 | 実際の損益 ÷ 1R。計画どおりの LC なら −1R 前後 |
| 見送り | 計画を立てた（または入りたくなった）が、入らなかった取引 |
| 判定 | 決済後に計画と実行から自動で付ける分類（5.3） |

## 4. 記録の形（データ）

利用者ごとに分ける（`users/{uid}/...`）。計算に要る値は円と銘柄の価格の単位で持ち、表示用の丸めはしない。

### 4.1 銘柄（Instrument）

利用者ごとの一覧。初回に代表的な銘柄（株価指数・FX・商品・仮想通貨）を候補として出し、利用者が足す。

| 項目 | 例（架空） | 備考 |
|---|---|---|
| 名前 | `US30` | |
| 種類 | 株価指数 / FX / 商品 / 仮想通貨 / 株式 / その他 | 集計の切り口 |
| 価格の通貨 | `USD` | 円なら為替は 1 で固定 |
| 乗数 | `1` | 価格が 1 動いたときの 1 数量あたりの損益（価格の通貨）。CFD は 1、先物は取引単位 |
| 説明 | | 任意 |

### 4.2 取引（Trade）

1 取引 = 1 文書。状態は `計画中 → 保有中 → 決済済み`、または `見送り`。

**計画（エントリー時に決めること。保有中になったら確定し、以後の変更は履歴に残す）**

| 項目 | 必須 | 備考 |
|---|---|---|
| 銘柄・L / S | ○ | |
| イン（予定 / 実際） | ○ | |
| LC | △ | 空のまま入ることもできるが、判定は C（5.3）になる |
| 崩れの条件 | △ | LC の根拠の文章。空なら「LC の根拠なし」の印 |
| TP | | 根拠からの推定 |
| 数量 | ○ | 許容リスクからの提案値を出す（AC1） |
| 資金・許容リスク | ○ | 設定から写す |
| 根拠 | ○ | 文章 + セットアップのタグ（例: リバ狙い・ブレイク・トレンドフォロー。利用者が育てる） |
| エントリー時の感情 | | タグ（例: 冷静 / 負けを取り戻したい / 儲けたい / 焦り / 退屈 / 怖い）+ 短いメモ |
| チャート | | 画像 3 枚まで |
| 計画を記録した時刻 | 自動 | |

**実行**

| 項目 | 備考 |
|---|---|
| エントリーの時刻 | 計画の時刻より前なら「後付けの計画」の印（AC4） |
| LC の変更の履歴 | 時刻・前 → 後・理由・広げた / 詰めた（AC2） |
| 決済の時刻・価格 | |
| 為替（決済時） | 円建ての銘柄は 1 |
| 決済の理由 | 自己申告: LC（崩れの条件に当たった）/ TP / 根拠が崩れたので手で / 崩れる前に怖くなって / 時間切れ / その他 |
| 決済時の感情 | タグ + メモ |
| 総評 | 自由記述 |

**導出（保存せず、計算で出す。5 章）**: 損益（円）、1R、R 倍数、リスク（%）、判定と理由。

### 4.3 見送り（Pass）

取引と同じ文書で状態が `見送り`。計画の項目は任意で、加えて:

| 項目 | 備考 |
|---|---|
| 種類 | 躊躇した（根拠はあったが入れなかった）/ 我慢した（根拠が無いのに入りたくなったが入らなかった） |
| 感情 | タグ + メモ |
| その後の価格 | 任意。入っていたら TP / LC のどちらに先に当たったかを後から記録する |

### 4.4 気づき（Insight）

| 項目 | 備考 |
|---|---|
| 日付・内容 | |
| 関係する取引 | 0 件以上。取引の詳細からも気づきを書ける |
| タグ | 取引の根拠・感情と同じタグを使える |
| 出どころ | 自分 / AI の振り返りから採用 |

### 4.5 設定

資金（変更の履歴つき）、許容リスク（既定 1%。0.5〜3% の範囲で設定。2% を超えると警告）、表示の通貨（円）、テーマ。

## 5. 計算と判定

計算はすべて **純関数**（DOM・通信・現在時刻に依存しない）。画面と API の両方から同じ規則で使えるよう、規則は TypeScript の純関数を正とし、API が判定を保存・集計に使う場合は同じテストの例（JSON の表）を Python でも通す（判断待ち D6）。

### 5.1 損益と R

- 符号 `s` = L なら +1、S なら −1
- 損益（円）= `s × (決済 − イン) × 数量 × 乗数 × 為替`
- 1R（円）= `|イン − LC| × 数量 × 乗数 × 為替`（LC が無ければ定義しない）
- R 倍数 = 損益 ÷ 1R
- リスク（%）= 1R ÷ 資金 × 100
- 計画のときの為替は、決済時の為替が分からないので「計画時の為替」（利用者の入力。円建ては 1）で 1R を出す

例（架空）: L、イン 100.00、LC 99.50、数量 10,000、乗数 1、為替 1、資金 1,000,000 円 → 1R = 5,000 円、リスク 0.5%。決済 99.40 → 損益 −6,000 円、−1.2R。

### 5.2 許容リスクからの数量の提案（AC1）

最大の数量 = `資金 × 許容リスク ÷ (|イン − LC| × 乗数 × 為替)` を、銘柄の数量の刻みに切り捨てる。LC を動かすとその場で変わる。

### 5.3 判定（A / B / C）

オーナーのシートの考え方（A = 決めた LC で切れた、B = LC を下げた・過剰リスク・許容リスクありきの LC、C = LC を決めずに遅れた）を土台に、**計画と実行の記録だけから** 決める。上から順に最初に当たったもの。

| 判定 | 条件 | 理由の表示（例） |
|---|---|---|
| C（極悪） | エントリー時に LC が無い | 「LC を決めずに入った」 |
| C（極悪） | 損失が 1R の `C_LATE` 倍（既定 2 倍）を超えた | 「LC から大きく遅れた（−2.6R）」 |
| B（悪い） | LC を広げた（リスクを増やす向きに動かした） | 「LC を広げた（99.50 → 99.20）」 |
| B（悪い） | 計画のリスクが許容リスクを超えていた | 「過剰リスク（2.8%）」 |
| B（悪い） | 損失が 1R の `B_LATE` 倍（既定 1.2 倍）を超えた | 「LC より遅れた（−1.4R）」 |
| B（悪い） | 崩れの条件が空（LC の根拠が無い = 金額ありきの LC の疑い） | 「LC の根拠が書かれていない」 |
| A（いい） | 上のどれにも当たらない損失 | 「計画どおりの LC」 |

- 利益の取引にも同じ規則で「計画どおりだったか」を付ける（例: LC 無しで勝った取引は「計画外の勝ち」）。勝ちでも計画外は良い取引として数えない
- 「崩れる前に怖くなって決済」は損失を小さくするが、計画からの逸脱として別に数える（早逃げ）
- 判定は手で上書きできるが、上書きした事実と元の判定は残す（集計は両方出せる）
- 閾値 `B_LATE`・`C_LATE` は判断待ち D5

### 5.4 後付けの計画

計画の記録時刻がエントリーの時刻より後なら「後付け」の印を付け、集計では分けて数える（後付けの計画は、計画どおりだったかの証拠にならない）。

## 6. 集計（規律の指標）

期間・銘柄・種類・セットアップ・感情・曜日 / 時間帯で絞り込める。

| 指標 | 中身 | 何が分かるか |
|---|---|---|
| 計画どおり率 | 判定 A（と計画内の勝ち）の割合 | 規律が守れているか |
| 判定ごとの件数と損失 | A / B / C の件数・損失の合計 | どの種類の負けが多いか |
| 避けられた損失 | B / C の損失のうち、1R を超えた分の合計 | 規律だけで減らせた金額 |
| R の分布 | R 倍数のヒストグラム | −1R で切れているか、左に長い裾があるか |
| 平均 R・期待値 | 1 取引あたりの平均 R | 手法の優位性（規律と分けて見る） |
| リスク（%）の分布 | 計画のリスク | 過剰リスクの頻度 |
| LC を広げた回数 | | |
| 早逃げ・粘りの回数 | 決済の理由の自己申告 | 恐怖・期待に負けた回数 |
| 感情別の成績 | エントリー時の感情ごとの計画どおり率・平均 R | どの心理のときに崩れるか |
| 負けの後の取引 | 損失の直後（同じ日・次の取引）の計画どおり率 | リベンジトレードの傾向 |
| 見送りの検証 | 見送りのうち、入っていたら TP / LC だった数 | 躊躇の癖・我慢の効果 |

## 7. AI の振り返り

### 7.1 何をするか

- **取引ごと**: 決済のあとで、計画・実行・判定・感情・総評を読み、「計画どおりだったか」「崩れた点」「次に同じ場面でどうするか」を短く返す。採用すれば気づきとして保存できる
- **期間ごと**: 期間（週・月）の取引・見送り・気づきを読み、規律が崩れるパターンを、根拠になった取引を挙げて指摘する（例: 「負けた直後の取引で LC を広げた例が 3 件」）
- AI は売買の推奨（どこで入れ・何を買え）をしない。規律と心理の振り返りに限る

### 7.2 作り

- AI の呼び出しは API（サーバー）から行う。ブラウザに資格情報を置かない
- 送るのは、その利用者の記録のうち振り返りに要る項目だけ（チャート画像は利用者が選んだときだけ）
- 利用者ごとの 1 日の回数の上限と、全体の 1 日の費用の上限を持つ（option-simulator の費用の計上の仕組みを参考にする）
- 利用者への説明: 記録の一部が AI の提供元に送られることを、初めて使うときに示して同意を得る
- 資格情報とモデルは判断待ち D3

## 8. 画面

### 8.1 原則

- モダンでかっこいい SPA（K2）。ダークを既定にし、ライトも用意する。数字は等幅で大きく、損益・判定は色だけに頼らず符号とラベルを添える
- スマホ（360px）から PC まで同じ機能。入るときはスマホで素早く、振り返りは PC で広く
- 入る前の操作は最小の手数で: 銘柄・L / S・イン・LC を入れれば、リスク（%）と提案の数量がその場で出る
- 取り消せる操作は確認を出さず [元に戻す] で戻す
- option-simulator の `docs/ui-guidelines.md` の原則（一目で読める・操作の一貫性・戻るで迷わない・どの幅でも崩れない など）を、実装の最初の Issue で loss-note 向けに移植する

### 8.2 画面の一覧

| 画面 | 中身 |
|---|---|
| ホーム | 保有中の取引（LC までの距離・リスク）、今週の計画どおり率、最近の判定、[新しい計画] |
| 新しい計画 | 銘柄・L / S・イン・LC・崩れの条件・TP・数量（提案つき）・根拠・感情・チャート。[エントリーした] / [見送った] |
| 保有中 | LC の変更（広げると警告）、[決済] |
| 決済 | 決済の価格・時刻・為替・理由・感情・総評 → 判定と R をその場で表示 |
| 取引の一覧 | 絞り込み・並べ替え。判定・R・リスクの列。チャートは小さく |
| 取引の詳細 | 計画と実行の時系列（計画 → エントリー → LC の変更 → 決済）、判定の理由、気づき、AI の振り返り |
| 振り返り | 6 章の指標のダッシュボードと、期間の AI の振り返り |
| 気づき | 一覧・タグ・関係する取引 |
| 設定 | 資金・許容リスク・銘柄・タグ・テーマ・データの書き出し・アカウントの削除 |

## 9. 作り（構成）

```
ブラウザ（SPA: Vite + Preact）
   │  Firebase Authentication で発行された ID トークン
   ▼
Cloud Run（1 つのサービス）
   ├─ 画面の静的ファイル（dist/）
   └─ API（Flask）: トークンを検証 → uid で範囲を絞って読み書き
         ├─ Firestore（記録）
         ├─ Cloud Storage（チャート画像。非公開のバケット）
         └─ AI の提供元（振り返り）
```

| 項目 | 案 | 理由 |
|---|---|---|
| ログイン | Firebase Authentication（Google ログイン + メールのリンク） | GCP の中で完結し、SPA から使いやすい。SaaS なので IAP は使わない |
| 記録の読み書き | API 経由（ブラウザから Firestore を直接触らない。Firestore のセキュリティルールは全部拒否） | 判定・計画の確定（変更を履歴に残す）・利用者ごとの分離を 1 か所で守れる。テストしやすい |
| チャート画像 | Cloud Storage の非公開バケット。アップロードと表示は API が発行する短い期限の署名付き URL | 画像は利用者の個人の情報。公開しない |
| 計算 | 画面の純関数（TypeScript）が正。API は保存・集計で同じ規則を使う | 入力中の即時の表示と、集計を同じ規則に |
| インフラ | Terraform（`infra/bootstrap` = 所有者が apply、`infra/prod` = CI が apply）。option-simulator と同じ分け方 | |
| CI / CD | GitHub Actions、Workload Identity Federation、Environment `prod` の承認 | |

### 9.1 セキュリティとプライバシー

- 利用者の分離は API で強制する（すべての読み書きが、検証したトークンの uid の範囲に限られる。AC6 をテストで固定）
- CSP（インラインの script / style なし、HTML 文字列を DOM に入れない）
- ログに記録の中身・メールを出さない（uid は出してよいが、記録の中身と結び付けて残さない）
- データの書き出し（JSON / CSV）とアカウントの削除を MVP に入れる（自分のお金の記録を預ける人への最低限の約束）
- 利用規約・プライバシーポリシーは、オーナー以外の利用者を受け入れる前に用意する（判断待ち D8）

## 10. オーナーのデータの取り込み（K7）

- シートを CSV に書き出し、手元の `data/local/`（gitignore）に置く
- 使い捨てのスクリプトで、オーナーのアカウントに取り込む（スクリプトの置き場所は `scripts/`、実データはリポジトリに入れない）
- 取り込んだ取引は「取り込み」の印を付ける。計画の時刻が無いので後付けの計画として扱い、判定は「LC の変更の履歴が無い」前提で付く（集計では分けて見られる）
- 「〃」は直前の行の値を引き継ぐ。チャート画像はシートから取り出せる範囲で取り込む（取り出せなければ取り込まない）
- 為替・損益はシートの値をそのまま使い、5.1 の式で出した値と食い違う行は件数だけを報告する

| 項目 | 目標 |

| API | 通常の読み書き 300 ms 以内（コールドスタートを除く） |

### 13.2 判断待ち（オーナー）

| # | 論点 | 推奨 | 選択肢 |
|---|---|---|---|
| D1 | 記録の読み書きの経路 | API 経由（9 章） | A: API 経由 / B: ブラウザから Firestore を直接（セキュリティルールで守る。サーバーの処理は減るが、計画の確定・履歴をルールで守るのが難しい） |

### 13.3 実装時に決めるもの

ディレクトリの構成、タグの初期値、銘柄の初期の候補、画面の細部、テストの例の表の形。

### 13.4 リスク

| リスク | 対策 |
|---|---|
| 入力が面倒で記録が続かない | 入る前の必須項目を最小にし、スマホで 30 秒以内に計画を残せることを目標にする。後付けも許す（印を付けるだけ） |
| 自己申告（決済の理由・感情）が正直でない | 判定は自己申告に頼らない記録（LC の履歴・時刻・価格）だけで決める |
| 他人のお金の記録を預かる責任 | 利用者の分離のテスト、書き出しと削除、ログに中身を出さない、規約・ポリシー |
| AI の費用 | 回数と費用の上限。期間の振り返りは手動で起動 |
| AI が売買の助言をしてしまう | 振り返りの指示で規律と心理に限定し、評価の例で確かめる |
