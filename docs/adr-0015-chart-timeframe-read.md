# ADR-0015: チャートの時間足の表示の読み取りは、明細の読み取りの送り口・守り・1 日の上限を共有し、書かれた表記を純関数で列挙に直す

- 状態: 採用
- 日付: 2026-11-18
- 関連: Issue #27、EPIC #10（終了条件 11）、Issue #12（チャートの枠と手で選ぶ時間足）、ADR-0005（読み取りの入口・共有のパッケージ）、ADR-0006（チャート画像の保存）、ADR-0010（1 日の上限）、ADR-0011（資格情報の方式）、設計書 5.3・5.6 #20・7.5・8.2、0.2 の C13・C14・C27・C38

## 背景

#12 で、記録する画面にエントリー時・決済時のチャートの枠と、手で選ぶ時間足の欄を入れた。両方の時間足があれば、判定は「時間足を変えた（…・チャートから）」の B を本人の申告に頼らずに出せる（設計書 5.6 #20）。ところが欄を手で選ぶのは記録の手間の予算（事後に 1 回、30 秒。設計書 1.1 の 0）を食い、選ばれなければ比較は働かない。チャートに写っている時間足の表示（「4H」「日足」など）を読み、欄を埋めたい。

読み違いは偽の B を作り、判定への不信につながる（設計書 13.2「自動判定がトレーダーの実感と合う」）。チャートの画像は利用者の個人の情報で、AI の提供元に送ることになる。

## 決定

1. **送り口は明細の読み取りと同じものを使い、「読み取りの種類」だけを差し替える**。共有のパッケージに `task.ReadTask`（指示・画像に添える決まった文・ツールの名前・説明・入力の形・結果の検査）を置き、送り口 `agent_reader.Reader` は種類を引数で受ける（既定は明細の `STATEMENT_TASK`。明細の振る舞いは変えない）。子の環境・要求ごとの一時ディレクトリ・締め切り・フック・失敗の分類は種類によらず同じ。チャートの種類は `chart_timeframe.CHART_TASK`（ツール `report_chart_timeframe`）
2. **AI は書かれた表記を返し、列挙への直しは純関数**（C27 と同じ考え）。結果は `kind`（`chart` / `not_chart`）と `timeframe_written`（16 文字以下・英数・空白・日本語の時間足の言葉に要る字だけ）の 2 つ。外れたら全体を捨てる（502 `read_invalid_result`）。`timeframe_of` が NFKC・空白の除去の後に型ごとの規則（日本語・MT 型・数だけ・数 + 単位・英語の言葉）で 9 つの列挙（1 分足〜月足）に直す。**読めない・列挙に無い足・2 通りに読める表記は空**（読み違えるより空。空なら判定は壊れない）。「1M」は月足と 1 分足の 2 通りに読めるので空、「M1」「15M」などは分、「M」「MN」「月足」は月足。価格・エントリーポイントは読まない（K11）
3. **API は `POST /api/chart-reads`**（画像の生のバイト。明細の入口と同じ順と守り: 認証 → 資格情報と SDK → 画像の上限 → 系統の名前 → ID トークン → 1 日の上限の予約 → 送る → 精算 → 検査 → 直し）。応答は `{"kind", "timeframe"}`（列挙か null）だけで、書かれた表記は応答・ログに出さない（ログは時間足が読めたかの件数 `rows` = 1 / 0 だけ）。画像も結果も保存しない（チャートは [記録する] で取引と一緒に保存する。ADR-0006）
4. **1 日の上限は明細の読み取りと同じ財布**: 利用者ごとの回数・利用者ごとの費用・全体の費用を同じ日の文書・同じ判定の順で合わせて数える（ADR-0010 の結果の節の宿題。#51・ADR-0014 の形）。バイパスのリストの利用者は明細と同じく利用者ごとの上限を受けず、全体の上限は受ける。上限の値の形の誤りは明細と同じく AI を呼ばずに 503 `read_unavailable`。**予約額は種類ごと**（`ReadLimits.chart_reserve_micro_usd`。`pricing.reserve_micro_usd` に読み取りの種類を渡し、チャートの指示・ツールの定義のバイト数と最大出力から出す）。Sonnet 5.5 でチャートは **130,164 µUSD**（入力の上界 27,541 トークン × 4 µUSD + 最大出力 2,000 × 10 µUSD）、明細は 278,736 µUSD のまま（#66 から 282,012 µUSD。ADR-0017）。精算は実額（コードレビュー B1。予約が重なって利用者ごとの費用の上限に早く当たるのを避ける）
5. **モデル・effort・締め切りは明細と同じ**（`app_settings`）。**最大出力はチャートだけ 2,000 トークン**（`APP_CHART_MAX_OUTPUT_TOKENS`）。結果は 2 つの欄だけで、最も長い形（表記 16 文字の漢字）でも JSON で約 80 B。明細の合成 14 枚の実測の出力は平均 720 トークン以下（結果の JSON が数百〜数千 B のとき）で、結果の外の出力（ツールの呼び出しの枠など）を含めてもチャートは数百トークンに収まる見込み。その数倍の余裕を取った。チャートの実際の出力はまだ測っていないので、AC-7 の実測（道具の `eval-charts --preset app` はこの最大出力で読む）で失敗（最大出力で止まる）が出たら上げる
5a. **先立ての CLI（#65・ADR-0013）は使わない**。先立ては明細の指示・ツールで立ち上げた 1 つで、記録する画面を開いたときの準備は明細の読み取りのため。チャートで使うと明細の読み取りがその場の起動を待ち、種類ごとに先立てを持つと待たせる CLI と費用の見積もりが増える。チャートの読み取りは入力と並んで進むので、その場の起動の数秒は 30 秒の予算の中で重なる（AC-8 で測る）
6. **画面**:
   - 枠の画像が使えるようになったら追加の操作なしで送り、枠の時間足が空で利用者が触っていなければ埋めて印「チャートから」（札 + 欄の左の線）を付ける
   - **AI の読み取りは 1 つずつ送る**（明細が先、チャートはその後に枠の順。明細の読み取り中に貼ったチャートは明細の応答の後、送っているチャートがあれば明細はその後）。同時の予約（B1）と 1 vCPU の CLI の起動の取り合い（N5）を減らす。送る前に差し替えた・外した枠は送らない
   - **読み取り中も [記録する] を押せる**（記録が失敗して編集に戻ったら、止めた読み取りを同じ順の約束で送り直す。時間足は任意の欄。帯に「待たずに記録できます」（時間足の読み取り中は枠に「時間足を読み取っています…」））。記録した時点で終わっていない読み取りは止めて結果を捨て、時間足は利用者が選んだ値（無ければ空）のまま保存する（デザインレビュー 1・コードレビュー N3。main の決定）
   - 利用者が違う値を選んでいれば上書きせず、欄の下に「チャートからは 〈日足〉 と読めました [日足にする]」を出す（1 タップで直せる。押したときだけ置き換えて印）
   - 3 つ目のタップ（時間足を変えたか）の答えが「変えず」「短い足へ」で、チャートの時間足が長い足へ変わっているときは、判定の理由の 2 行目に「あなたの答え: 変えず ／ チャート: 4 時間足 → 日足」、タップの下に「チャートでは 4 時間足 → 日足」を並べる（責める語・警告の色を使わず、どちらを正とするかを迫らない）
   - 差し替え・外す・離れたで止め、後で届いた応答は捨てる。失敗・読めない・チャートでないは決まった文言で知らせ、欄は空のまま
   - 送る前の注意は主語を分ける: 明細の枠に「明細の画像は AI の提供元（Anthropic）に送って読み取り、保存しません。…」、チャートの枠の見出しの下に「時間足を読むため AI（Anthropic）に送ります。チャートは記録と一緒に保存します。」（C38）。全長の上限（#33 AC-4）は、狭い画面でチャートの枠の余白とプレビューの高さを詰めて保つ
7. **精度は合成のチャートで測る**（`tools/statement-eval` の `generate-charts` / `eval-charts`）。架空の銘柄名で、凡例・MT 型・日本語・数だけ・選ばれたボタンの表示の形と、表示なし・列挙に無い足・時間足の違う 2 つ・チャートでない画像の 14 枚。合否は「表示があるのに列挙の別の値に読み違えた件数 0」と「表示が無いのに値を作った件数 0」（空は許す）。実際の AI は手元で流すときだけ

## 選択肢

- **チャート用に別の送り口・別の部品を作る**: 子の環境・一時ディレクトリ・締め切り・フックの守りが 2 つに分かれ、片方だけ直す事故が起きる。採らない
- **AI に列挙を直接選ばせる**: 書かれた表記と列挙の対応（「1M」を月足と読むか 1 分足と読むかなど）がモデルの中に隠れ、テストで固定できない。採らない（C27）
- **チャート用に別の上限を置く・上限の値を上げる**: 天井が増える（ADR-0010 の決定 1 の「全体 2.00 USD」の意味が変わる）。採らない（B1 の案 3。main の決定）
- **予約額を明細と同じにする（最初の案）**: 明細 1 + チャート 2 の予約が重なると、その日の計上額が 163,792 µUSD を越えたあたりから 3 つ目が利用者ごとの費用で 429 になる（明細が断られることもある）。採らない
- **読み取り中は保存しない（最初の案）**: 任意の欄のために最長 30 秒 [記録する] を止め、30 秒の予算とぶつかる。採らない（読み取りを待たずに記録でき、終わっていない結果は捨てる）
- **「チャートでない」と読めたら保存を止める**: 読み違いで正しいチャートが保存できなくなる。知らせるだけにする

## 結果

- 1 取引でチャートを 2 枚貼ると、明細と合わせて 1 日の回数を 3 回使う（回数の上限 30 回なら 1 日 10 取引まで）。費用は実額で数えるので、通常（1 回の実額は数万 µUSD）は回数の上限が先に効く
- 予約が重なったとき（画面は 1 つずつ送るが、止めた要求の予約は API の精算まで残る）に、その日の利用者の計上額 P で明細 1 + チャート 2 が何件通るか（既定の上限: 利用者 1.00 USD・全体 2.00 USD。予約額は明細 278,736・チャート 130,164 µUSD。#66 で明細が 282,012 になり、下の表の境目は 457,660（3）・457,661（2）・717,988（1）に移る。テストは予約額の式で境界を書く）:

  | P（µUSD） | 通る件数 |
  |---|---|
  | 0 / 150,000 / 460,936 | 3 |
  | 460,937 | 2（3 つ目のチャートが利用者ごとの費用で 429） |
  | 721,264 | 1 |
- 追記（#89・2026-11-19）: 追加のチャート（最大 5 枚）も時間足を読むために送るので、1 取引の記録で最大 明細 1 + チャート 7 = 8 回読む（回数の上限 30 回なら 1 日 3 取引で上限に当たる）。編集の画面の差し替え・追加も 1 回ずつ同じ財布で数える。上限は API が強制するので費用の天井は変わらない。回数が先に効くなら、追加の枠だけ読み取りを省く案を検討する（ADR-0006 の追記）

  画面が 1 つずつ送るので、実際に重なるのは差し替え・記録で止めた直後の予約だけ（`api/tests/test_chart_read.py` の例で固定）
- 本番の 1 vCPU・1 GiB で、画面が 1 つずつ送るので、同時に動く CLI は先立て 1 + その場の 1 の最大 2 つ（ADR-0013 で 1 つ約 165 MB）。明細の読み取りの秒数への響きは AC-8 の測り直しで見る
- 読み取りの指示・最大出力を変えるときは予約額が変わる（種類ごとに `pricing` で出すので、ずれない。チャートの予約額が明細の半分より小さいことをテストが見る）
- 直す画面（取引の詳細からの差し替え）では読まない（手で選ぶまま）。読むなら後の Issue
