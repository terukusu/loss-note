# ADR-0014: AI の上限に利用者ごとの費用を足し、上限を受けない利用者（バイパス）のリストを持ち、上限の値を環境変数で変えられるようにする

- 状態: 採用（ADR-0010 の決定 1 の「上限は 2 つ・値はコードの定数」を上書き）
- 日付: 2026-11-18
- 関連: Issue #51、#62（使った量の見える化。同じ数え方で見せる）、EPIC #45、ADR-0010（1 日の上限・予約 → 精算）、ADR-0011（資格情報の方式）、ADR-0003（許可リストの照らし方）、設計書 8.2、`infra/README.md`「AI の上限とバイパス」

## 背景

ADR-0010 の天井は「利用者ごとの回数（30 回）」と「全体の費用（2.00 USD）」の 2 つだった。回数は 1 回の重さ（費用）を見ないので、1 人の利用者（画面の不具合の連打・盗まれたトークン・予約額のまま残る失敗の続き）が全体の 1 日の額を 1 人で使い切れる。そうなると、その日のほかの利用者の読み取りがすべて 429 になり、記録が手入力に戻る。

一方、オーナー自身（運営者）が利用者ごとの上限で止まると、上限そのものの確かめや、まとめての取り込みができない。上限を外すにはコードの定数を変えてデプロイし直すしかなかった。

## 決定

1. **上限は 3 つ**: 利用者ごとの回数（既定 30 回）・**利用者ごとの費用（既定 1.00 USD / 日）**・全体の費用（既定 2.00 USD / 日）。判定の順は 回数 → 利用者の費用 → 全体の費用。費用はどちらも「計上額 + 予約額 ≤ 上限」なら送る（等しいときは送る）。越えたら AI を呼ばずに 429 `read_limited`（理由はログだけ: `limited_user` / `limited_user_spend` / `limited_spend`）
2. **利用者の日の文書に金額を残す**: `users/{uid}/statement_read_days/{日付}` = `{count, microUsd}`。予約で全体と同じだけ足し、精算で利用者と全体の 2 つを 1 回の書き込み（バッチ）で実額に直す。金額が欠けた・負の文書は 0 として扱わず「数えられない」として、その日の回数 × 予約額に見積もる（多めに数える側。`read_limits.effective_user_micro`）。欠けるのは #51 より前の文書と、切り戻した日に前のコードが利用者の文書を `{count}` で置き換えたとき、負になるのは新しいコードの予約と精算の間に前のコードの予約が挟まったとき。数え方は方式によらない（`oauth_token` の額は「従量課金なら」の換算額）。#62 の見える化はこの文書を読む
3. **バイパスのリスト**: 環境変数 `LOSS_NOTE_AI_BYPASS_EMAILS`（カンマ区切りのメール。本番は Secret Manager の `loss-note-ai-bypass-emails` の参照）。照らし方は許可リスト（#43）と同じ純関数（確かめ済みのメール・ASCII だけ小文字に寄せる・完全一致）。リストの利用者は利用者ごとの回数と費用の上限を受けない。**全体の上限（ブレーカー）は受ける**。計上には残す。未設定・空ならバイパスの利用者は 0 人（許可リストの「エミュレーターで未設定なら制限しない」とは逆に、閉じる側）。バイパスは使えるかどうかに影響しない
4. **上限の値は環境変数で変えられる**: `LOSS_NOTE_AI_USER_DAILY_COUNT`（0〜999999 の整数）・`LOSS_NOTE_AI_USER_DAILY_USD`・`LOSS_NOTE_AI_DAILY_USD`（整数部 6 桁・小数 6 桁まで。Decimal で整数の µUSD に直し、浮動小数を通さない）。未設定・空なら既定。空白だけの値は「空」でなく形の誤り。**形の誤りは既定値に戻さず、読み取りを 503 `read_unavailable`**（ログの理由 `limit_config` と、誤っている変数の名前 `var`。値は出さない。AI を呼ばない・数えない）。読み取りの準備の入口（`POST /api/statement-reads/prepare`。#65）も同じく 503 にする（CLI を立てない）。準備は AI を呼ばず費用が無いので、利用者の上限（回数・費用）は見ない。値の上の天井（極端に大きい値）はコードで設けない（整数部 6 桁まで）。最後の歯止めは提供元の Console の月の上限（ADR-0010 決定 7）に任せる。本番は repository variables `AI_USER_DAILY_COUNT`・`AI_USER_DAILY_USD`・`AI_DAILY_USD`（値を伏せる必要の無い数。ADR-0011 決定 6 と同じ例外）→ Terraform の変数（同じ形の検査で plan で止める）→ Cloud Run の環境変数。指定したものだけ載せる
5. **本番のバイパスの参照は切り替えで付ける**: Terraform の `ai_limit_bypass`（既定 false。CI は repository variable `AI_LIMIT_BYPASS` が `true` のときだけ）。版の無い参照ではインスタンスが起動しないので、版を入れてから切り替える（ADR-0010 決定 6 と同じ理由）
6. 名前は `AI`（明細の読み取りに限らない）: 後の AI の振り返り（設計書 8.1）・チャートの時間足の読み取り（#27）を同じ財布で数えるかはそれぞれの Issue で決めるが、入れるときはこの上限と文書を使う

## 既定値（利用者ごとの費用 1.00 USD）の理由

- 全体 2.00 USD の半分: 1 人が暴走しても、同じ日のほかの利用者に少なくとも 1.00 USD が残る
- 予約額（Sonnet 5.5 で 278,736 µUSD）の 3 回分（836,208）が入るので、1 人が同時に 3 枚まで送れる（4 回分は入らない）
- 通常の実額（1 回 数万 µUSD）では回数の上限 30 回が先に効く。費用の上限は、予約額のまま残る失敗（締め切り超え・精算の失敗）が続く場面や 1 回が重い場面の天井

## 選択肢

- **値をコードの定数のままにする**（ADR-0010）: 上限を変えるたびにコードの変更とデプロイが要り、汎用の作り（誰でも clone して自分の上限で使う）にも合わない。採らない。代わりに「形の誤りは閉じる側」で、設定の誤りで上限が外れる経路を塞ぐ
- **形の誤りを既定値に戻す**: 下げるつもりの誤記（例: `0,5`）で高い既定値が効く。採らない
- **バイパスは全体の上限も外す**: お金が出ていく口の天井を誰にも外させない（盗まれたトークンでもオーナーのアカウントなら外れる）。採らない
- **バイパスの利用者を計上しない**: 全体の計上と利用者の計上の合計が合わなくなり、#62 で使った量を見せられない。採らない
- **バイパスを許可リストの入れ物に印を付けて持つ**: 2 つの意味を 1 つの値に混ぜると、使える利用者を変えるたびにバイパスも変わりうる。入れ物を分ける
- **利用者ごとの費用の上限を全体と同じ 2.00 USD にする**: 1 人で全体を使い切れるので、足す意味が無い。採らない

## 結果

- 読み取り 1 回の書き込みは変わらない（予約のトランザクション 1 回と精算のバッチ 1 回。精算は 1 文書から 2 文書に）
- 本番で上限を変える・バイパスを付けるのは repository variable と deploy だけで済む（コードを変えない）。バイパスのリストの入れ物は bootstrap の apply が要る（create 2）
- 切り戻した日（前のリビジョンが要求を受けた日）は、前のコードが利用者の文書を `{count}` で置き換えて金額が消える・負になることがある。新しいコードは欠け・負を回数 × 予約額に見積もるので少なめには数えないが、置き換えの後に新しいコードが書いた 0 以上の金額は、その日の実額より少なめのことがある。全体の文書は前のコードも同じ形で書くので、全体の上限（ブレーカー）はその日も効く
- 利用者ごとに上限を変える・課金は課金の EPIC
- 使った量の見える化（#62）: `GET /api/ai-usage` が本人の日の文書（決定 2）だけを、日本時間の今月 1 日〜今日の範囲で読む（最大 31 件・書かない）。返すのは今日・今月の回数と金額（判定と同じ見積もり）、本人に効く上限の値、バイパスか、今日の次の読み取りが本人の上限で止まるか。全体の上限は値だけ返し、全体の日の文書（全体の使った量）は読まない・返さない（利用者が 1 人でも、全体の額から自分の額を引けばほかの利用者の使い方が分かるため）。方式も返さない（どの方式でも従量課金の料金表で換算した額と画面に書く）。上限の値の形の誤りは 503 `read_unavailable`（決定 4 と同じ閉じる側）
