# ADR-0013: 明細の読み取りの CLI を、CPU が割り当てられている間に 1 つ先に立て、1 回の読み取りで捨てる

- 状態: 採用
- 日付: 2026-11-18
- 関連: Issue #65、#60（起動の段の準備・時間の内訳のログ）、ADR-0005（読み取りの送り口。結果の「要求ごとに CLI の子を起動する」を読み替える）、ADR-0009（Cloud Run の設定）、ADR-0010（上限の予約と精算）、ADR-0011（3 つの方式・子の環境の許可リスト・ID トークンのファイル）、設計書 1.1 の 0・7.5・10 章

## 背景

#60 の後の本番の測り直しで、読み取り 1 回は全体 6.7 秒、うち AI の応答（`api_ms`）は 1.84 秒で、約 4.7 秒は要求ごとに Claude Code の CLI を起動して終わらせる手間だった。記録の手間の予算（事後に 1 回、30 秒以内）の中で、貼ってから欄が埋まるまでの待ちは利用者が何もできない時間で、長いと貼らずに手で写すようになる。

本番は最小 0 台・要求の処理中だけ CPU（ADR-0009。`cpu_idle = true`）。最小インスタンス数や CPU の常時割り当てで CLI を常に温めておくのは、費用が増えるので使わない（オーナーの指示 2026-11-18）。要求を処理していない間は CPU がほぼ止まるので、要求の合間に裏で CLI を立てても進まない。

## 決定

1. **先立ては CPU が割り当てられている間にだけ行う**: (a) 起動の段（#60 の `warmup` の段 `cli`。立て始めるだけで、立ち上がりを待たない = 起動を延ばさない）、(b) 準備の要求 `POST /api/statement-reads/prepare`（記録する画面を開いたときに画面が 1 回送る。認証・使える利用者の許可リストは読み取りの入口と同じ blueprint の門。AI を呼ばず、1 日の上限に数えない。立ち上がるまで最大 20 秒待って 200 `{"ready": bool}`。使えない設定・SDK なしは 503 `read_unavailable`）
2. **先立ては 1 つのインスタンスに最大 1 つ・使い捨て**: 1 つの先立て = 要求ごとの一時ディレクトリ 1 つ + SDK の `query()` 1 回。読み取りが 1 回使ったら、CLI を止めて一時ディレクトリごと消し、それから応答を返す（応答の後は CPU が止まりうるので、画像を含む一時ファイルの削除を後回しにしない。手元の実測で入力を閉じてから CLI が終わるまで 0.05 秒以下）。1 つの CLI を複数の読み取りで使い回さない（前の要求の画像・会話が CLI に残る）。次の先立ては、また (a) か (b) のとき
3. **作り**: 共有の部品 `statement_read.warm.WarmPool`。背後のスレッド 1 本の asyncio の event loop で、先立ての起動から後始末までを 1 つの task で行う（SDK のクライアントは同じ async の文脈で使う決まり）。SDK の `query()` は「子の起動 → initialize → prompt の stream を読む」の順なので、prompt の generator の最初の yield を仕事が渡されるまで待たせる（読まれ始めた = 立ち上がった）。子の環境・一時ディレクトリは `agent_reader.option_kwargs` そのもの（ADR-0005・ADR-0011 のまま）
4. **締め切り**: anyio の `CancelScope` の deadline を段ごとに付け替える。起動の上限 20 秒 → 立ち上がったら「作ってから 10 分」→ 読み取りが取ったら「取った時点から 20 秒」（ADR-0005 の決定 6 の締め切りと後始末の作りのまま）
5. **戻り道**: 先立てが無い・期限切れ・画像を送る前に失敗した（起動の失敗など）ときは、残りの時間でその場で CLI を立てて読む（今までの経路。AI へ送るのは 1 回、上限に数えるのも 1 回）。同時に 2 つの読み取りが来たら、先立てを取るのは lock の下で 1 つだけで、2 つ目はその場で立てる
6. **期限と後片付け**: 使われない先立ては作ってから 10 分（`app_settings.APP_WARM_TTL_SECONDS`）で捨てる。取るときに Python の時計でも確かめる（CPU が止まって loop の deadline が遅れても古い先立てを使わない）。プロセスの終了（atexit）で先立てを取り消して一時ディレクトリを消す。SIGKILL などで後始末が走らなくても、子の CLI は親が消えると入力の終わりで止まり、Cloud Run の一時ディレクトリはメモリでインスタンスと一緒に消える（ADR-0005 と同じ限界）
7. **federation の ID トークン**: 先立てを立てるときに ID トークンを取り、`cred/identity-token`（0600）に置いてから CLI を起動する（同梱の CLI 2.1.316 は起動の近くでもファイルを読む）。読み取りの要求は今までどおり要求ごとに ID トークンを取り（予約の前。取れなければ 502・数えない）、送る直前に同じパスへ置き換える（一時ファイル + rename。CLI のファイルの provider は交換のたびにファイルを読む）。期限 10 分は ID トークンの期限 1 時間より十分短い。CLI が起動の段で交換を済ませて結果を cache した場合は、実際の交換に使われるのは先立てのとき（10 分以内）に取った同じ SA のトークンになる
8. **ログ**: 読み取りの `statement_read` に `cli`（`warm` / `cold` の 2 値）を足す（AC の判定と本番の測り直し用。`read_ms − api_ms` が CLI の側の時間）。準備の要求は `event=statement_read_prepare`・`reason`（`ok` / `not_ready` / `unavailable`）・`ms` だけ。起動の段の時間に `cli_ms`

## 選択肢

- **最小インスタンス数 1・CPU の常時割り当て**: 裏で次を立てられ最も速いが、常時の費用がかかる。オーナーの指示で採らない
- **1 つの CLI を使い回す（会話を続ける）**: 2 回目から速いが、前の要求の画像・会話が CLI の中に残り、別の利用者の読み取りに混ざりうる。採らない
- **読み取りの直後（応答の後）に次を立てる**: `cpu_idle` では応答の後に CPU が止まって進まない。採らない（読み取りの要求の中で次を立てる案は、応答が遅れる分と比べて後で測る）
- **結果を受けたらすぐ返し、後始末は裏で**: 応答の後は CPU が止まり、画像を含む一時ファイルの削除が次の要求まで遅れうる。終わらせる時間は 0.05 秒以下と小さいので採らない
- **Anthropic の API を直接呼ぶ**: 最も速いが oauth_token が使えず、終了条件 8 を測った経路が変わる（ADR-0005 の選択肢）。採らない

## 結果

- 記録する画面を開いて準備が済んでから貼った読み取りは、CLI の起動を待たない（偽の SDK で起動の時間が `read_ms` に入らないことを確かめた）。本番の速さ（`cli = warm` の回の `read_ms − api_ms`）はデプロイの後に測る
- 費用: 準備の要求は CLI が立ち上がるまで（本番の見積もり 3〜4 秒）要求を開けておくので、1 回あたり約 4 vCPU 秒 + 4 GiB 秒（Cloud Run の要求ごとの課金で約 0.0001 USD）。記録する画面を開いた時点で取引・銘柄・設定の要求が同じインスタンスを起こすので、起動を増やさない。待っている CLI は要求の外では課金されない
- 待っている CLI 1 つで約 165 MB のメモリ（手元の RSS）を使う。同時の読み取りは今までどおり CLI を同じ数だけ立てるので、先立ての分 +1
- 本番の起動の段で立て始めた CLI が、起動の CPU boost の後に CPU が止まって立ち上がりきらないことがある。その先立ては準備の要求か読み取りが来たときに続きが進む（読み取りが取れば立ち上がりの残りを待つ）
- 記録の API が使えない設定（`make_unconfigured_blueprint`）では準備の入口は 404（画面は応答を使わない）
- 評価の道具（`tools/statement-eval`）は今までどおりその場で立てる（先立てを使わない）

## 追記: Issue #99 で決めたこと（2026-11-19）

背景: #65 の後の本番の読み取りは全体 5.0 秒、うち AI の外（`read_ms − api_ms`）が約 2.9 秒残った。手元で同梱の本物の CLI を、送り先を手元の偽の Messages API に向けて測る（実際の AI は呼ばない）と、立ち上がった先立ての AI の外は約 0.15〜0.23 秒（CPU 1 つに固定）で、本番の 2.9 秒を再現しない。本番だけで効く要因を見分けられるように内訳をログに出し、費用をかけずに外せる要因を先に外す。

9. **段の時間のログ**: 読み取りのログ（`statement_read`）に送り口の段ごとの時間を足す（`agent_reader.Stages`。進んだ段だけ・数だけ）。`wait_ms` = CLI が画像を受け取れるまで（先立ての立ち上がりの残り、その場で立てたときは起動）・`first_ms` = 画像を渡してから CLI の最初の message まで・`result_ms` = 結果まで・`turn_ms` = CLI が報告するターンの時間・`close_ms` = 結果から CLI が終わって一時ディレクトリを消すまで。`read_ms` ≈ `wait_ms` + `result_ms` + `close_ms`。`turn_ms − api_ms` が CLI の中の AI の外、`result_ms − turn_ms` が送り口と CLI の間の受け渡し
10. **準備の要求で静まりまで待つ**: CLI は SDK の initialize に答えた後も、止めていた起動の仕事（手元の同梱の CLI 2.1.316 で 5 つ。プラグイン・設定の書き込みなど）を続ける（手元で CPU 約 0.14 秒）。応答の後は CPU がほぼ止まるので、準備の要求が先に返るとこの仕事は次の読み取りの要求の中に持ち越される。準備の要求は、立ち上がった後に先立ての CLI の CPU 時間（`/proc` の stat。親がこのプロセスで cwd が一時ディレクトリの `cwd` の子だけ）が 1 秒の間に 10 ms 以下しか増えなくなるまで、最大 5 秒（`app_settings.APP_WARM_SETTLE_SECONDS`）待ってから返す（同梱の CLI は立ち上がった後 約 0.3・0.6・1.0・1.5 秒の時点で小さな仕事を流し、間は 0.3〜0.5 秒静か。1.0 秒は CLI が起動の仕事を止めておく上限。窓はそれより長くとる。手元で静まりまで約 2.6〜2.8 秒）。読めない環境では待たない。待った時間は準備のログの `settle_ms`（読めなければ 0）。費用は準備の要求が最大 5 秒長く開く分（#65 の見積もりの範囲。最小インスタンス・常時の CPU は使わない）
11. **会話を保存しない**: 明細・チャートの読み取りの CLI（先立て・その場で立てる・評価の道具）を `--no-session-persistence`（SDK の `extra_args`）で起動する。CLI は画像を受けると一時ディレクトリの中に画像の写し（`images/`。fdatasync つき）と画像の base64 を含む会話の記録（`projects/*.jsonl`）を書いていた。この指定で両方とも書かなくなる（手元の同梱の CLI 2.1.316 で strace で確かめた。読み取りの結果は同じ）。ディスクへの書き込みが減り、画像の写しが一時ディレクトリの中にも残らない（ADR-0005 の「画像を保存しない」に沿う）。help には「--print のときだけ」とあるが、SDK の起動（`--output-format stream-json --input-format stream-json`）でも効く。SDK・CLI を上げるときに確かめ直す

レビューの後に足したこと（#99）:

- 画面の準備の要求の打ち切りは 30 秒（立ち上がり 20 秒 + 静まり 5 秒より長く、Cloud Run・gunicorn の 60 秒より短い）
- 静まりを待つ間に CLI が自分で終わったら、準備の応答は `ready: false`・ログの `reason` は `ended`（立ち上がらなかった `not_ready` と分ける）。同じ先立てで静まりを確かめた後の準備は待たない（`settle_ms` = 0）
- 先立てを取ったが画像を送る前に失敗して、その場で立て直した回はログの `cli` を `cold_retry` にし、段の時間を先立てを取った時刻から数える（`wait_ms` に先立てで待った時間を含め、`read_ms` ≈ 段の和を保つ）
- 起動の段の設定の取得: 同梱の CLI は既定の送り先のとき、起動の段で remote managed settings と policy limits を Anthropic の API から取る（`CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` では止まらない。立ち上がりの前なので先立ての読み取りには入らない）。送り先は、子の環境に `ANTHROPIC_BASE_URL` などの送り先の変数が名前ごと無い（ADR-0011 の許可リスト）ので既定の Anthropic だけ。federation では、CLI のソースの文字列で remote settings の取得が WIF のトークンの cache（`getWIFTokenCache`）を使う作りになっていることから、起動の段で ID トークンを交換し、交換した資格情報で同じ取得をする見込み（交換が起動の段に入り、読み取りの段の交換が減る）。外へ要求を出して確かめてはいない。本番のログの `wait_ms`・`turn_ms − api_ms` で読む
- SDK・同梱の CLI を上げるときは、`--no-session-persistence` を CLI が受け付けて会話の記録と画像の写しを作らないことを確かめ直す（CLAUDE.md「開発」の依存の節）

採らなかったもの:

- **結果を受けたらすぐ返し、CLI を終わらせるのは応答の後**: 手元で結果から終わりまで約 0.03〜0.05 秒と小さく、上の「選択肢」の理由（応答の後は CPU が止まる）が残る。本番の `close_ms` が大きければ見直す
- **`--bare`（`CLAUDE_CODE_SIMPLE`）**: 起動の仕事を減らせるが、Anthropic の資格情報を `ANTHROPIC_API_KEY` だけに限り、oauth_token・federation が使えない
- **CLI の内部の切り替え（`CLAUDE_CODE_DISABLE_STARTUP_WORK_GATE` など）**: 版ごとに意味が変わりうる内部の環境変数で、手元で効果が見えない
- **思考（thinking）・effort・最大出力を下げる**: AI の側（約 1.8 秒）を縮めうるが、精度の比べ（評価の道具の合成の明細）が要る。別の Issue
