# ADR-0006: 根拠の足のチャート画像は API が中継し、Firestore に取引と同じトランザクションで置く

- 状態: 採用
- 日付: 2026-11-18
- 関連: Issue #12（根拠の足のチャートを保存して判定につなぐ）、#9（取引の詳細で 2 枚を並べる。差し替え / 外すの画面は別 Issue）、#27（時間足の表示の読み取り）、EPIC #10（終了条件 5）、設計書 0.2 C22・4.2・5.3・7.5・10 章・10.1、ADR-0004（記録の API の認証と保存先）、ADR-0005（画像の上限・画像を残さない・multipart を避けた理由）

## 背景

根拠の足のチャート（エントリー時・決済時の 2 枚）は、利用者の個人の情報（何をいつどの向きで持ったか）である。「本人しか読めない」「消せば残らない」が守れなければ利用者は貼らなくなる（Issue #12 の why）。設計書 10 章は「非公開のバケット。アップロードと表示は API が発行する短い期限の署名付き URL」としていたが、C22 で「手元のエミュレーターで署名付き URL の守りを確かめられなければ、API が中継する」と決めていた。

#12 の計画で、Firebase の Storage のエミュレーターに V4 の署名付き URL を作って試した（架空の鍵・架空の画像。状態コードだけを記す）:

| 試したこと | 結果 |
|---|---|
| 正しい署名の GET | 200 |
| 署名を 1 文字変えた GET | 200 |
| A の署名のまま B のパスへ | 200 |
| 署名のクエリを外した GET | 200 |
| 期限（2 秒）を過ぎた GET | 200 |
| GCS の JSON API の media の GET（認証なし） | 200（ルールも通らない） |
| Firebase の REST の GET（認証なし） | 403（ルールは効く） |

エミュレーターは署名を検査しないので、改ざん・他人のパス・期限切れの守りを手元のテストで固定できない。

## 決定

1. **保存と表示は API の中継**（C22 のとおり）。アップロードも読み戻しも API を通り、画面は Firestore・Storage を直接読まない（ルールは全部拒否のまま）。利用者の分離は API のテスト（記憶の保存先・エミュレーターの Firestore の両方）で固定する
2. **画像のバイト列は Firestore に置く**。場所は `users/{uid}/charts/{tradeId}-{slot}`（slot = `entry` / `exit`。1 文書 = 1 枚、`{contentType, data}`）。取引の文書には要約（形式と大きさ）だけを持つ。場所は API が uid・取引 ID（英数字だけ）・枠（2 つだけ）から作り、利用者の送ったパス・名前を使わない
3. **取引とチャートは 1 つのトランザクション**で書く（作成・取引の削除・差し替え・外す）。チャートを書けなければ取引も無く、取引を消せばチャートも無い（R4）。補償の処理・掃除の仕組みは要らない
4. **入口**: 作成は `POST /api/trades` の multipart（部分 `record` = JSON の文字・`entryChart` / `exitChart` = 画像。どちらも任意。JSON の本文も今のまま受ける）。差し替え `PUT`・外す `DELETE`・読み戻し `GET` は `/api/trades/{id}/charts/{slot}`（差し替えの本文は画像の生のバイト）。読み戻しは保存した形式の `Content-Type`・`no-store`・`nosniff`
5. **multipart は記憶の中だけで読む**: Flask の request_class で Werkzeug のファイルの部分の受け皿を `BytesIO` にする（既定は 500 KiB を超えるとディスクの一時ファイル。ADR-0005 が multipart を避けた理由）。作成の multipart だけ、本文全体 64 KiB + 2 × 500,000 B + 8 KiB・部分 3 つ・文字の部分 64 KiB を上限にする。ほかの入口は 64 KiB のまま
6. **画像の上限は明細と同じ**（PNG / JPEG・500,000 B・長辺 2,000 px。共有の `statement_read.image.check_limits`）。画面は送る前に端末で描き直す（#15 の `prepareImage`）
7. **チャートの時間足**（`entryChartTimeframe` / `exitChartTimeframe`）は、その枠にチャートがある取引にだけ持つ。無い枠に時間足は 400 `noChart`（作成・取引の直し）。外すとその枠の時間足も消える。**差し替えるとその枠の時間足は消して選び直しにする**（前のチャートの足が残って、誤って「時間足を変えた」の B を出さない。#27 の読み取りが入れば読み取りで埋まる）
8. 依存は足さない（google-cloud-storage を使わない）

## 選択肢

- **署名付き URL + Cloud Storage**（設計書 10 章の元の案）: 画面が直接バケットに送れて API の負荷が軽い。しかし手元のエミュレーターで守りを確かめられない（上の表）。署名者の権限（IAM の signBlob）・バケットの CORS・CSP の `img-src` / `connect-src` の追加も要る。採らない
- **中継 + Cloud Storage**: 守りは API で確かめられるが、取引（Firestore）と画像（Storage）が別の保存先になり、「画像を置く → 取引を書く → 失敗したら画像を消す」の補償が要る。プロセスが途中で落ちると孤児の画像が残り、掃除の仕組みが要る（スコープの拡大）。採らない
- **中継 + Firestore**（採用）: 1 トランザクションで原子的に書け、CI のエミュレーターの結合のテスト（Firestore）がそのまま使える。1 文書の上限（1 MiB）に 500,000 B は収まる（エミュレーターで 2 枚 × 500,000 B + 取引を 1 トランザクションで書けること、1 MiB 超は拒まれることを確かめた）

## 結果

- 費用: Firestore の保存の単価は Cloud Storage より高い。1 枚 0.5 MB × 2 枚 × 1,000 取引 ≈ 1 GB / 利用者の規模。読み書きは 1 枚 1 回の文書の読み書き
- 1 取引の作成で約 1 MB を書く（Firestore の 1 要求 10 MiB の内側）。本番での速さは縦切り 2 で確かめる
- **見直しの条件と移す道**: 1 取引に 3 枚以上にする（設計書 4.2）・上限を上げる・費用が効くときは、保存先の約束 `Store`（`api/src/loss_note_api/store.py`）の後ろで Cloud Storage へ移す。API の入口と画面は変わらない（中継のまま。補償と掃除の仕組みを一緒に作る）
- Storage は使っていないが、ルールは全部拒否のままで、エミュレーターの検査（Firebase の REST の読み・書きが未認証・本人のトークンで 403）を `npm run test:api:emulator` に足した
- 取引の詳細（#9）は 2 枚を並べて見せるだけ（読み戻しの GET を canvas に描く）。差し替え・外すの画面は別 Issue。記録する画面は、枠に入れ直すと時間足が空に戻る（決定 7 と同じ考え）

## 追記: 編集の画面のチャートと付属のチャート（2026-11-19・Issue #89）

- **枠を広げる**: エントリー時・決済時の 2 枠に、付属のチャートの枠 `x1`〜`x5` を足す（最大 5 枚。1 取引で合わせて 7 枚まで）。置き場は今と同じ `users/{uid}/charts/{tradeId}-{slot}`（slot は 7 つの決まった名前だけ）。取引の文書の要約 `charts` も枠ごと（ある枠だけ）。付属は判定に使わない（「時間足を変えた（チャートから）」はエントリー時・決済時の 2 枠だけ）
- **付属の記録の形**: 並び（追加した順）・任意の時間足・任意の一言（40 字まで）は記録の `extraCharts`（`[{slot, timeframe?, note?}]`）。`extraCharts` の枠と付属の画像のある枠は一致する（画像の無い行は 400 `extraCharts` の `noChart`、行の無い画像は 400 `{slot}Chart` の `noEntry`）。付属の無い取引には鍵が無い（既存の取引は今のまま読める）。直しの本文に `extraCharts` が無ければ保存済みの並び（残る枠だけ）を保つ（古い画面が黙って付属を落とさない）
- **上限**: 1 枚の上限は今と同じ（PNG / JPEG・500,000 B・長辺 2,000 px）。1 取引の合計は枚数で 7 枚（最大 3.5 MB。1 文書 1 枚なので文書の 1 MiB の上限に当たらず、1 要求のトランザクションの 10 MiB の内側）。multipart の入口の上限は、本文全体 64 KiB + 7 × 500,000 B + 16 KiB・部分 8 つ（記録 + 枠ごとに 1 つ）にする。読み戻しは枠ごとの GET を並行に（詳細・編集）。画面の保存の時間の上限は送る大きさで延ばす（30 秒 + 1 MB ごとに 10 秒。7 枚で 70 秒）
- **見直しの条件に当たったが Firestore のままにする**: 結果の節の見直しの条件（1 取引に 3 枚以上）に当たる。それでも Firestore のままにする。理由: 1 文書 1 枚なので文書の 1 MiB の上限に当たらない（1 枚 500,000 B）。7 枚を書く 1 要求は約 3.5 MB で 1 要求の 10 MiB の内側（エミュレーターで 499,000 B × 7 枚の作成・差し替え・削除を確かめた）。利用者は当面オーナー 1 人で、保存の費用は小さい。取引とチャートを 1 トランザクションで書ける利点（補償・掃除が要らない）が大きい。次の見直しの条件: 1 枚の上限を上げる・1 取引の枚数を 7 枚より増やす・利用者を広げて保存の費用が月の予算に効く・本番で 7 枚の保存が遅い（after-deploy で測る）
- **時間足の読み取りの回数**（ADR-0015 の追記）: 追加のチャートも時間足を読むために送るので、1 取引の記録で最大 明細 1 + チャート 7 = 8 回読む（1 日の回数の上限 30 回なら 1 日 3 取引で上限に当たる）。編集の画面の差し替え・追加も 1 回ずつ同じ財布で数える。上限は API が強制するので費用の天井は変わらない。回数が先に効くなら、追加の枠だけ読み取りを省く（判定に使わない）案を価値と回数の引き換えとして検討する
- **編集の保存の約束**: 取引の直し `PUT /api/trades/{id}` が multipart（部分 `record` + 差し替え・足す画像 `{slot}Chart` + 外す枠 `removeChart`（枠の名前。枠ごとに 1 つ。同じ枠に画像と外すの両方は 400 `conflict`））も受け、取引と枠ごとのチャートの文書（置く・消す）を **1 つのトランザクション** で書く。画面は [保存する] を押すまでチャートを送らず、[キャンセル]・画面を離れると捨てる。差し替えの画像が使えなければ前のチャートのまま（保存で消さない）。チャートを先に送る（即時）・順に送る案は、途中の失敗で取引とチャートが食い違う（差し替えた枠の時間足が消えた取引が残るなど）ので採らない。`?snapshot=current`（#31）も同じ要求に付けられる
- **時間足**: 足した枠の時間足は画面で空から時間足の読み取り（ADR-0015）で埋める。編集の画面でエントリー時・決済時を差し替えたときは、決定 7 の「選び直し」を画面では「前に保存した時間足を残し、読めたときだけ置き換える（読み取りが失敗で終わったときだけ残す。読み取りの途中で保存したら「指定なし」で保存し、帯で知らせる）」に改める（読めないたびに時間足が消えて、判定の理由が黙って変わるのを防ぐ。#89 のデザインの再レビュー。main の決定）。利用者が直せば利用者の値。API の枠ごとの入口は今のまま（差し替えで時間足を消す）。直しの本文の時間足は、直した後にチャートのある枠にだけ（無ければ 400 `noChart`。決定 7 と同じ）。枠ごとの入口（PUT / DELETE `/charts/{slot}`）は今のまま使え、付属の枠では並びに無ければ末尾に足し（差し替え）、外すと並びからも消す
